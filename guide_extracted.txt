Project Goal & Definition of Done
GOAL OF THIS DEMO
 
Build a fully clickable, realistic-looking, mobile-first betting website
that a non-technical founder can open on a laptop or phone and confidently
demo live in front of a client, with zero crashes and zero placeholder
“Lorem ipsum” text anywhere in the primary user flows.
 
DEFINITION OF DONE — the demo is finished when all of these are true:
• A visitor can land on the homepage, register with a phone number,
  verify a (simulated) OTP, and land in a logged-in dashboard in under
  60 seconds, with zero manual database edits required.
• The visitor can add demo funds, browse at least 3 football leagues with
  realistic odds, build a multi-bet slip, place a bet, and see it appear
  in their bet history as “pending”.
• At least one match is shown as LIVE with odds that visibly change every
  few seconds without a page refresh.
• Keno, the Aviator-style crash game, and virtual football are all fully
  playable end-to-end with a simulated outcome and updated balance.
• An admin can log into /admin, see live-looking KPIs, approve a pending
  withdrawal, and override the odds on one sample match.
• The whole app is usable (not broken, not unreadably slow) on a
  throttled “Slow 3G” mobile profile.
• The app is deployed to a public URL on a $0/month hosting tier that the
  founder can send to a client right now.

Bet Slip Business Logic
BET SLIP BUSINESS LOGIC — implement precisely, both client- and
server-side (never trust the client-side number alone):
 
Odds multiplication (Multi/Accumulator)
total_odds = odds_1 * odds_2 * ... * odds_n
potential_return = stake * total_odds
Example: 1.50 * 1.80 * 2.00 = 5.40 total odds; a 100 ETB (demo) stake
returns 540 (demo) on a full win.
 
Correlated-market rule
A user may never combine two selections from the SAME match inside one
multi-bet. Detect this the instant a second selection from an already-
used match_id is added: show an inline red warning on the new
selection, keep the older one, and disable the “Place Bet” button
until it is resolved.
 
Limits (all editable from /admin, never hardcoded)
• Minimum stake: 10 (demo units); Maximum stake: 10,000 (demo units)
• Multi-bet: minimum 2 legs, maximum 20 legs
• Maximum payout per ticket: 500,000 (demo units) — cap silently
  applied server-side even if the multiplied odds imply more
 
Odds-integrity check on placement
On “Place Bet”, the server re-reads the current odds for every
selection and compares them to what the client submitted. If any
differ, reject the placement, return the new odds, and have the
client show the “Odds have changed — accept new odds?” modal rather
than silently placing at a different price.
 
Bet lifecycle
pending -> won | lost | void | refunded, always written through a
single settlement function so history stays consistent; settling a
bet must atomically update the user’s wallet balance and write a
Transaction row in the same database transaction.

Live Odds & Real-Time Architecture
REAL-TIME ARCHITECTURE
 
Use a single realtime channel strategy across the app (Socket.IO OR
Supabase Realtime — pick one, do not mix). Define and use these
logical event/channel names consistently:
 
odds:update        { matchId, marketName, selection, value }
match:live-event   { matchId, minute, type, description }
match:status       { matchId, status, isLive }
keno:draw-start    { drawId, closesAt }
keno:draw-result   { drawId, numbers }
aviator:round-start{ roundId, startedAt }
aviator:multiplier { roundId, value }
aviator:crash      { roundId, crashAt }
wallet:balance     { userId, balance }
 
If a true WebSocket server is impractical on the chosen free host,
simulate the same effect with 3–5 second client-side polling against
a lightweight GET endpoint — the visible behavior (numbers updating
without a page refresh) must be indistinguishable to the user either
way.
 
A background job (can be a simple setInterval-driven service or a
scheduled serverless function) must continuously nudge pre-match odds
by small random deltas and drive the live match clock/events so the
demo feels alive even with nobody else connected.

Game Engine Specifications
CUSTOM GAME ENGINES — self-built, RNG-based, clearly documented
 
Keno
• Draw 20 numbers from a 1–80 pool using a seeded RNG every 60–90
  seconds; store the seed and drawn numbers on the Draw record
• Player picks up to 10 numbers before the countdown hits zero; payout
  multiplier is looked up from a fixed pay table keyed by
  (numbers picked, numbers matched) — hardcode a standard Keno pay
  table as a constant
 
Aviator-style crash game
• Each round, pre-generate a crash point using something like:
    crashPoint = max(1.00, (0.99 / (1 - random())) rounded to 2dp)
  with a house-edge constant folded in (document the exact formula
  and constant you land on in the README) — store it server-side and
  never expose it to the client before the round ends
• Client renders a multiplier that climbs from 1.00x based on elapsed
  time (e.g. exponential curve), driven by server ticks so it can
  never be raced by client manipulation
• “Cash Out” locks in whatever multiplier the server confirms at the
  moment the request is received, server-side, before the crash tick
 
Virtual football
• Pick two fictional team names per fixture, generate a plausible
  final score with a weighted random goal model (e.g. Poisson-ish
  weighting so 1–2 goals per side is most common), and pre-compute
  1X2 / Over-Under odds from the same model so pricing looks
  internally consistent
• Animate a simple event ticker (kickoff, a couple of goal/chance
  events at random timestamps, full-time) across a fixed 60–90
  second real-time window

Data & Odds Provider Strategy
DATA / PROVIDERS — free or self-built ONLY for this demo
 
• Primary source: a self-built mock-data generator/seed script that
  creates realistic leagues, fixtures, teams, and odds so the app
  runs fully offline and never breaks on a third party’s rate limit
• Optional enrichment: a free-tier public odds API (e.g. The Odds API
  free tier, ~500 requests/month) for a handful of real upcoming
  fixtures. Cache responses aggressively (e.g. 5–10 minutes) and
  fail over to mock data automatically if the key is missing or the
  quota is exhausted — the app must never show an error state to
  the visitor because of this
• No genuine free production-grade casino/virtual-games provider
  exists. Real providers (Digitain, BetConstruct, Altenar,
  SoftGamings, NuxGame, EveryMatrix, Golden Race, Inbet) all require
  a signed commercial/licensing agreement and are NOT usable in a
  public demo — this is why Section 9’s custom game engines exist
 
Document in the README, in a simple table, exactly which pieces of
data are “real free-tier data” vs. “self-generated demo data” so the
founder can accurately describe the demo to a client.
 
For the README’s production roadmap section only (do not build now):
Digitain / BetConstruct / Altenar / SoftGamings / NuxGame as future
real sportsbook+casino aggregator candidates, and Telebirr / CBE Birr
B2C APIs as future real payment rails — both require a signed
commercial agreement and the NLA betting license before they can be
connected for real.

Prerequisites
• A GitHub account (free) to host the repository
• A Vercel account (free Hobby tier) — sign up at vercel.com using
  “Continue with GitHub” so the two are linked automatically
• A Supabase account (free tier) — sign up at supabase.com
 
Step 1 — Push the code to GitHub
1. git init (if not already a repo)
2. git add . && git commit -m "feat: initial demo MVP"
3. Create a new empty repository on github.com (do NOT initialize it
   with a README, to avoid conflicts)
4. git remote add origin <your-repo-url>
5. git branch -M main && git push -u origin main
 
Step 2 — Create the free Postgres database on Supabase
1. In the Supabase dashboard, click “New project”, pick a name and a
   region close to Ethiopia/Europe, and set a strong database
   password (save it)
2. Once provisioned, go to Project Settings → Database → Connection
   string, and copy the “Connection pooling” URI — this becomes
   your DATABASE_URL
3. If you are using Supabase Realtime (Section 8) or Supabase Storage,
   also copy the Project URL and anon public key from Project
   Settings → API for NEXT_PUBLIC_SUPABASE_URL and
   NEXT_PUBLIC_SUPABASE_ANON_KEY
 
Step 3 — Run migrations and seed the database
1. Locally, put the Supabase DATABASE_URL into your .env file
2. npx prisma migrate deploy      (creates all tables on Supabase)
3. npx prisma db seed             (populates the demo data from
   Section 16)
4. Open Supabase’s Table Editor and spot-check that Users, Matches,
   and Odds rows are actually there before moving on
 
Step 4 — Create the Vercel project
1. In the Vercel dashboard, click “Add New” → “Project”
2. Import the GitHub repository you pushed in Step 1
3. Framework Preset: Vercel auto-detects “Next.js” — leave Build
   Command as "next build" and Output Directory as the default;
   do not override these unless you have a reason to
 
Step 5 — Add environment variables in Vercel
Before clicking Deploy, open the “Environment Variables” section on
the same import screen (or later under Project → Settings →
Environment Variables) and add every variable from Section 15’s
.env.example with its real value, in particular:
• DATABASE_URL            → the Supabase connection-pooling URI
• NEXTAUTH_URL             → your Vercel URL, e.g.
   https://your-project.vercel.app  (update after first deploy
   once you know the exact generated URL, then redeploy)
• NEXTAUTH_SECRET          → generate one locally with:
   openssl rand -base64 32
• ODDS_API_KEY              → optional; leave blank to run on mock
   data only, per Section 10
• NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_ANON_KEY → from
   Step 2, if used
• ADMIN_SEED_EMAIL / ADMIN_SEED_PASSWORD → the demo admin login you
   want to hand to the client
• DEMO_MODE=true            → always true for this deployment
 
Step 6 — Deploy
1. Click “Deploy”. Vercel installs dependencies, runs "next build",
   and gives you a live https://<project>.vercel.app URL, usually
   within 1–3 minutes
2. Go back into Settings → Environment Variables and correct
   NEXTAUTH_URL to the exact URL you were given, then trigger a
   redeploy from the Deployments tab so the corrected value takes
   effect
 
Step 7 — Real-time on Vercel (read this if you chose Socket.IO in
Section 8 instead of Supabase Realtime)
Vercel’s serverless functions do not keep a persistent process
alive, so a custom Socket.IO server cannot run inside the same
Vercel deployment. Two working options:
• Preferred for this demo: use Supabase Realtime channels instead of
  Socket.IO — it runs fine from Vercel’s serverless functions with
  no extra hosting
• If Socket.IO is required: deploy just the small Socket.IO server as
  its own free Web Service on Render.com (Render keeps a Node
  process alive persistently, unlike Vercel), then point
  NEXT_PUBLIC_SOCKET_URL in Vercel at that Render URL
 
Step 8 — Verify the live deployment
Open the live URL and manually run through the full Section 17 QA
checklist end-to-end on the deployed site, not just locally —
register, bet, play each game, and log into /admin.
 
Step 9 — Hand off to the client
Share the live URL plus the ADMIN_SEED_EMAIL / ADMIN_SEED_PASSWORD
admin login. Every future code push to the main branch on GitHub
auto-redeploys on Vercel, so updates before a client meeting are as
simple as: git push.

   README (real KYC, real Telebirr/CBE Birr integration, a licensed

   uptime/security hardening, per Section 10)
PERMISSIONS
 
You have full autonomy to install any npm/pip packages you need,
create or modify any files, choose specific free-tier services beyond
what’s named in this brief if they better serve the demo, and make
reasonable implementation-detail decisions without pausing to ask —
just note significant choices in the README’s “Decisions Made”
section.
 
Do not, under any circumstances, wire up real payment processors,
real gambling licenses/feeds that require a paid contract, or collect
real user KYC documents in this demo build.
